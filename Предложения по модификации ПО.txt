Предложения по модификации программного обеспечения
информационной системы учета заявок на ремонт автомобилей «АвтоТранс»

1. Улучшение пользовательского интерфейса

1.1. Адаптивная верстка и масштабирование
Предложение: реализовать автоматическую адаптацию размеров элементов интерфейса под разрешение экрана и масштаб системы.
Обоснование: на мониторах с высоким разрешением элементы могут выглядеть слишком мелкими.
Рекомендация по реализации: использовать относительные размеры (pack/grid с параметрами expand, fill), а также вычисление размеров окон относительно размеров экрана.

1.2. Фильтры и сортировка в списке заявок
Предложение: добавить возможность сортировки списка заявок по дате, статусу, клиенту и механикам, а также дополнительные фильтры (по роли, по диапазону дат).
Обоснование: улучшение удобства работы для менеджеров и операторов при большом количестве записей.
Рекомендация по реализации: расширить форму RequestsForm, добавить элементы управления сортировкой и изменить логику загрузки данных.

1.3. Цветовые индикаторы приоритетов
Предложение: добавить поле «приоритет заявки» с визуальным выделением (цветовая метка, иконка).
Обоснование: позволяет быстрее ориентироваться в критичных заявках.
Рекомендация по реализации: расширить таблицу Requests, добавить столбец priority и использовать дополнительные теги/цвета в Treeview.

2. Расширение функциональности статистики и отчетов

2.1. Диаграммы и графики
Предложение: реализовать визуальные диаграммы (например, распределение заявок по статусам, среднее время ремонта по типам авто).
Обоснование: наглядный анализ данных, удобный для менеджера и менеджера по качеству.
Рекомендация по реализации: использовать стороннюю библиотеку для построения графиков (например, matplotlib) и вывод графиков в отдельном окне статистики.

2.2. Экспорт отчетов
Предложение: добавить экспорт статистики и списка заявок в форматы CSV/Excel.
Обоснование: возможность дальнейшей обработки данных во внешних системах.
Рекомендация по реализации: реализовать формирование CSV‑файлов из результатов запросов к БД и предоставить пользователю выбор пути сохранения.

3. Улучшение работы с пользователями и безопасностью

3.1. Хранение паролей в хэшированном виде
Предложение: заменить хранение паролей в открытом виде на безопасные хеш‑функции (например, bcrypt или hashlib с солью).
Обоснование: повышение информационной безопасности и соблюдение лучших практик.
Рекомендация по реализации: изменить структуру таблицы Users (поле password), добавить функции генерации и проверки хэша при регистрации и авторизации.

3.2. Блокировка учетной записи при многократных неверных попытках
Предложение: реализовать блокировку учетной записи или временную задержку после нескольких неудачных попыток входа.
Обоснование: защита от перебора паролей.
Рекомендация по реализации: добавить поля для учёта количества попыток и времени блокировки, модифицировать функцию авторизации.

3.3. Разграничение доступа к данным
Предложение: расширить модель ролей, выделив дополнительные подроли и детализированные права (просмотр, редактирование, удаление).
Обоснование: более тонкая настройка полномочий в зависимости от должностных инструкций.
Рекомендация по реализации: описать матрицу прав для каждой роли и реализовать централизованную проверку прав в слое бизнес‑логики.

4. Интеграция и обмен данными

4.1. Импорт/экспорт справочников
Предложение: реализовать импорт и экспорт справочников пользователей и заявок из файлов CSV/Excel.
Обоснование: упрощение первоначального заполнения БД и переноса данных из legacy‑систем.
Рекомендация по реализации: добавить отдельное меню «Импорт/экспорт» для служебных ролей, реализовать функции чтения/записи файлов.

4.2. Интеграция с внешними сервисами уведомлений
Предложение: добавить отправку уведомлений по электронной почте или мессенджерам при изменении статуса заявки.
Обоснование: повышение оперативности взаимодействия с клиентами и механиками.
Рекомендация по реализации: внедрить модуль отправки уведомлений (SMTP, API мессенджера) и вызывать его при смене статуса заявки.

5. Повышение надежности и отказоустойчивости

5.1. Плановое резервное копирование
Предложение: настроить автоматическое ежедневное резервное копирование базы данных с ротацией копий.
Обоснование: снижение риска потери данных при сбоях оборудования.
Рекомендация по реализации: использовать планировщик заданий ОС (Task Scheduler в Windows) для периодического запуска отдельного скрипта резервного копирования.

5.2. Журналирование операций
Предложение: внедрить журналирование ключевых операций (создание/изменение/удаление заявок, авторизация, резервное копирование).
Обоснование: упрощение расследования инцидентов и контроль действий пользователей.
Рекомендация по реализации: добавить модуль логирования (logging) и запись событий в отдельный текстовый файл или таблицу Logs в БД.

6. Улучшение качества кода и тестирования

6.1. Автоматические модульные тесты
Предложение: добавить набор тестов для ключевых функций (авторизация, создание заявок, изменение статуса, статистика).
Обоснование: повышение надежности и упрощение сопровождения при изменении кода.
Рекомендация по реализации: использовать стандартный модуль unittest или pytest, оформить тесты в отдельной папке tests.

6.2. Проверка стиля кода
Предложение: использовать инструменты статического анализа (flake8, pylint) для регулярной проверки соблюдения соглашений об именовании и стиля.
Обоснование: единообразие кода и снижение количества скрытых ошибок.

Данные предложения могут быть реализованы поэтапно в зависимости от приоритетов заказчика и ресурсов на развитие системы.
