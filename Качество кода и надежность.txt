Качественные характеристики кода и надежность
информационной системы учета заявок на ремонт автомобилей «АвтоТранс»

1. Полнота обработки ошибочных данных

1.1. Валидация пользовательского ввода
В интерфейсе реализована проверка заполнения обязательных полей:
- при авторизации проверяется наличие логина и пароля;
- при регистрации заказчика контролируется заполнение всех полей и совпадение паролей;
- при создании заявки контролируется выбор клиента, типа автомобиля, заполнение модели и описания проблемы;
- при добавлении комментариев контролируется непустой текст комментария.

При нарушении правил ввода пользователю выводятся окна с понятным текстом и рекомендациями по исправлению (messagebox.showwarning/showerror).

1.2. Защита от некорректных операций
- при попытке удалить заявку система запрашивает подтверждение действия и предупреждает о необратимости;
- при отсутствии результатов поиска по фильтрам/строке поиска пользователю выводится информативное сообщение.

2. Контроль корректности входных и передаваемых данных

2.1. Ограничения на уровне базы данных
В модуле database.py при создании таблиц используются:
- первичные ключи для уникальной идентификации записей;
- внешние ключи с действиями ON DELETE CASCADE и ON DELETE SET NULL для поддержки ссылочной целостности;
- ограничения CHECK для допустимых значений ролей пользователей, типов автомобилей и статусов заявок;
- уникальный индекс на поле login в таблице Users для исключения дублирования учетных записей.

2.2. Логическая проверка в коде
Перед записью или обновлением данных выполняется:
- обрезка лишних пробелов (strip);
- проверка принадлежности статусу допустимому списку REQUEST_STATUSES;
- проверка выбранных значений в выпадающих списках (Combobox).

3. Обработка исключений и восстановление при сбоях

3.1. Обработка ошибок базы данных
Все функции доступа к БД в модуле database.py обернуты в блоки try/except/finally:
- при возникновении исключения выводится информативное диагностическое сообщение в консоль с префиксом [ERROR];
- соединение с БД в любом случае закрывается в блоке finally, что предотвращает утечки ресурсов;
- при ошибках модификации данных выполняется откат транзакции (rollback).

3.2. Резервное копирование
Реализована функция backup_database, создающая резервную копию файла базы данных в отдельном каталоге backup с отметкой времени.
Это позволяет восстановить состояние системы при сбоях оборудования или повреждении основного файла БД.

4. Наличие тестов и сценариев проверки

4.1. Функциональное тестирование
Для системы определены базовые тестовые сценарии:
- успешная и неуспешная авторизация пользователей разных ролей;
- создание заявки с корректными данными;
- попытка создания заявки с незаполненными обязательными полями (ожидается отказ и сообщение об ошибке);
- изменение статуса заявки и проверка корректного расчета даты завершения;
- добавление комментария к заявке;
- расчёт количества завершённых заявок и среднего времени ремонта;
- создание резервной копии базы данных и проверка появления файла в каталоге backup.

Результаты испытаний фиксируются в отдельном документе «Протокол тестирования».

4.2. Возможность автоматизации тестирования
Архитектура приложения разделяет:
- модуль работы с БД (database.py);
- слой моделей (models.py);
- слой интерфейса (ui.py).

Это позволяет при необходимости подключить модульные тесты (unittest/pytest) для функций database.py без запуска графического интерфейса.

5. Комментарии в коде и документирование

5.1. Комментарии в исходном коде
Комментарии присутствуют в местах, где требуется пояснение логики:
- описание назначения модулей и ключевых функций (database.py, ui.py, models.py);
- пояснения по режимам редактирования и ролям пользователей.

Комментарии не дублируют очевидные действия кода и служат для понимания архитектурных решений и неочевидных моментов.

5.2. Внешняя документация
К системе подготовлены следующие документы:
- блок‑схемы и текстовые описания алгоритмов (block_diagrams.md);
- руководство системному программисту (Руководство системного программиста XX);
- документ с предложениями по модификации ПО;
- настоящий документ, описывающий качественные характеристики кода и надежность;
- протокол тестирования с результатами выполнения ключевых сценариев.

6. Общая оценка качества и рекомендации

С точки зрения требований задания:
- реализована обработка большинства типовых ошибок ввода пользователем;
- обеспечена ссылочная целостность и базовая защита данных на уровне БД;
- предусмотрено резервное копирование и восстановление;
- реализовано разделение по ролям и ограничение доступа к данным;
- код структурирован по слоям (модели, БД, UI) и использует единый стиль именования (snake_case).

Рекомендуемые направления дальнейшего повышения качества:
- внедрение автотестов для ключевых функций работы с БД и бизнес‑логики;
- использование инструмента статического анализа кода для контроля стиля и потенциальных ошибок;
- расширение системы логирования и журналирования критичных операций;
- переход к хранению паролей в хэшированном виде и усиление механизмов авторизации.
