## Структура базы данных AutoService (ER-диаграмма)

Ниже описана концептуальная модель БД системы учёта заявок на ремонт (автосервис).  
Основные сущности: `Users`, `Requests`, `Comments`.

### Таблица Users (Пользователи системы)

- **userID** (INTEGER, PK, AUTOINCREMENT) — идентификатор пользователя.
- **fio** (TEXT, NOT NULL) — ФИО пользователя.
- **phone** (TEXT, NOT NULL) — телефон.
- **login** (TEXT, NOT NULL, UNIQUE) — логин для входа в систему.
- **password** (TEXT, NOT NULL) — пароль (в учебном примере хранится в открытом виде).
- **type** (TEXT, NOT NULL, CHECK) — роль пользователя:
  - `Менеджер`
  - `Менеджер по качеству`
  - `Оператор`
  - `Автомеханик`
  - `Заказчик`

### Таблица Requests (Заявки на ремонт)

- **requestID** (INTEGER, PK, AUTOINCREMENT) — идентификатор заявки.
- **startDate** (TEXT, NOT NULL) — дата приёма заявки.
- **carType** (TEXT, NOT NULL, CHECK) — тип автомобиля:
  - `Легковая`
  - `Грузовая`
  - `Внедорожник`
- **carModel** (TEXT, NOT NULL) — модель автомобиля.
- **problemDescryption** (TEXT, NOT NULL) — описание проблемы.
- **requestStatus** (TEXT, DEFAULT `Новая заявка`, CHECK) — статус:
  - `Новая заявка`
  - `В процессе ремонта`
  - `Готова к выдаче`
- **completionDate** (TEXT, NULL) — дата завершения ремонта.
- **repairParts** (TEXT, NULL) — использованные запчасти.
- **masterID** (INTEGER, NULL, FK → Users.userID) — назначенный автомеханик.
- **clientID** (INTEGER, NOT NULL, FK → Users.userID) — заказчик.

**Связи:**

- Один **заказчик** (`Users` с `type = 'Заказчик'`) может иметь много **заявок** (`Requests`).
- Один **автомеханик** (`Users` с `type = 'Автомеханик'`) может быть назначен на много **заявок**.
- При удалении заказчика (`clientID`) его заявки удаляются каскадно (`ON DELETE CASCADE`).
- При удалении механика (`masterID`) ссылка в заявке обнуляется (`ON DELETE SET NULL`).

### Таблица Comments (Комментарии к заявкам)

- **commentID** (INTEGER, PK, AUTOINCREMENT) — идентификатор комментария.
- **message** (TEXT, NOT NULL) — текст комментария.
- **masterID** (INTEGER, NOT NULL, FK → Users.userID) — автор комментария (обычно автомеханик или сотрудник сервиса).
- **requestID** (INTEGER, NOT NULL, FK → Requests.requestID) — заявка, к которой относится комментарий.
- **createdDate** (TEXT, DEFAULT CURRENT_TIMESTAMP) — дата и время создания комментария.

**Связи:**

- Одна **заявка** может иметь много **комментариев**.
- Один **пользователь** (механик/сотрудник) может оставить много **комментариев**.
- При удалении заявки или пользователя связанные комментарии удаляются (`ON DELETE CASCADE`).

### Индексы и ограничения целостности

- Первичные ключи: `Users.userID`, `Requests.requestID`, `Comments.commentID`.
- Внешние ключи:
  - `Requests.masterID` → `Users.userID` (SET NULL).
  - `Requests.clientID` → `Users.userID` (CASCADE).
  - `Comments.masterID` → `Users.userID` (CASCADE).
  - `Comments.requestID` → `Requests.requestID` (CASCADE).
- Уникальный индекс на `Users.login` предотвращает дубли логинов.
- Логические ограничения `CHECK` контролируют допустимые значения ролей, типов авто и статусов заявок.
- Для ускорения выборок добавлены индексы:
  - `idx_requests_status` на `Requests(requestStatus)`;
  - `idx_requests_client` на `Requests(clientID)`;
  - `idx_requests_master` на `Requests(masterID)`;
  - `idx_comments_request` на `Comments(requestID)`.

### Текстовая ER‑диаграмма (упрощённо)

```text
Users (userID, fio, phone, login, password, type)
   1 ────< Requests (requestID, startDate, carType, carModel, problemDescryption,
                     requestStatus, completionDate, repairParts,
                     masterID [FK Users], clientID [FK Users])

Requests (requestID)
   1 ────< Comments (commentID, message, masterID [FK Users], requestID [FK Requests], createdDate)

Роль пользователя (Users.type) определяет уровень доступа в приложении (оператор, менеджер, механик, заказчик и т.д.).
```

### Основной алгоритм учёта заявок (Модуль 1, кратко)

1. Пользователь запускает приложение и видит форму авторизации.
2. Пользователь вводит логин и пароль.
3. Программа проверяет учетные данные в таблице `Users`:
   - если данные неверны — выводит сообщение об ошибке и возвращается к пункту 2;
   - если данные верны — определяет роль пользователя.
4. В зависимости от роли открывается главное окно:
   - для оператора/менеджера/менеджера по качеству — меню работы со всеми заявками и статистикой;
   - для автомеханика — список только назначенных ему заявок;
   - для заказчика — список только его заявок.
5. Пользователь выбирает действие:
   - просмотреть список заявок с фильтрами;
   - создать новую заявку;
   - открыть детали выбранной заявки;
   - изменить статус заявки;
   - назначить/сменить автомеханика;
   - добавить комментарий;
   - просмотреть статистику;
   - выполнить резервное копирование БД.
6. Программа выполняет выбранное действие:
   - запрашивает и валидирует вводимые данные;
   - при ошибках ввода показывает информативные сообщения (ошибка/предупреждение/информация);
   - при удалении/неотвратимых действиях запрашивает подтверждение;
   - обращается к базе данных (`Requests`, `Users`, `Comments`);
   - обновляет интерфейс (списки, детальные формы, статистику).
7. Пользователь может вернуться назад в предыдущее окно или выйти из системы.

### Алгоритм функции расчёта среднего времени ремонта

Алгоритм соответствует функции `get_average_repair_time()`:

1. Открыть подключение к базе данных.
2. Выполнить запрос:
   - выбрать для всех заявок со статусом `Готова к выдаче` разность дат `completionDate - startDate` в днях.
3. Считать все полученные разности в список.
4. Если список пуст:
   - вернуть значение `0.0` (нет завершённых заявок).
5. Иначе:
   - вычислить сумму всех длительностей;
   - разделить сумму на количество элементов списка;
   - округлить результат до двух знаков после запятой;
   - вернуть полученное значение как среднее время ремонта.
6. Закрыть подключение к базе данных (всегда, даже при ошибке).
